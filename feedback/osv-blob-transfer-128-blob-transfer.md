# Trial feedback: nested-workspace iroh-blobs source transfer builds

- Agent/session: `osv-blob-transfer` (subagent; phase-2 source transfer in `experiments/osvauld-foundation`)
- Job ID(s):
  - Cargo, compile slot: 122, 123 and 124 failed as expected (red); 125 and 128 passed.
  - Python, `--run`: 126 failed as expected (red); 127 passed.
- Outcome: no issues observed with the coordinator. There was one minor friction point about discoverability.
- Redacted command, cwd type, resource class:
  - Compile slot: `tasks run --who osv-blob-transfer -- cargo test --offline [--locked] -j 2`. Job 128 ran `sh -c 'cargo test ... && cargo clippy ... -D warnings'`.
  - Run slot: `tasks run --who osv-blob-transfer --run -- env PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s tests -p test_linux_worker_contracts.py`.
  - The Cargo jobs ran in the live nested workspace cwd `experiments/osvauld-foundation`, reusing its existing nested `target` (user-approved). The Python jobs ran in the worktree root.
- What was exercised: real execution only. Seven jobs were submitted, approved, admitted, waited on and reported through `tasks run`. There were no detaches, timeouts, EAGAIN errors or resubmissions.
- Expected: queued admission under the `-j 2` default, plain-text output, and a final summary line with exit status.
- Observed:
  - Every job was admitted promptly. `tasks admission` showed zero PSI and about 25 GB available memory at the start, and no other live jobs.
  - Each run ended with `job N passed|failed (exit X) owner=osv-blob-transfer`, which made it easy to record IDs.
  - Red runs failed cleanly with Cargo's exit 101, which the coordinator propagated.
  - Job 122's failure was a real upstream dependency issue, not a coordinator issue: iroh-blobs 0.103.1's fs store uses `tokio::task::block_in_place` without enabling tokio's `rt-multi-thread` feature.
- Impact: none on the work. One friction point: `tasks list` prints the full job history as one JSON object (`jobs`, `estimates`, ...). To answer "is anything live right now?" I had to pipe it through a Python one-liner that filtered on `phase`. Interrupted historical jobs 48 and 55 (other owners) still appear as non-terminal `interrupted`, which makes a naive filter look busy.
- Suggested improvement: add `tasks list --active` or a short plain-text default. It would print one line per non-terminal job (id, phase, owner, resource, cwd) and keep the JSON behind `--json`, matching how `tasks logs` already behaves. Show `interrupted` jobs separately from queued or running ones.
- Acceptance test for suggestion: with one running compile job, one queued run job and one historical `interrupted` job in an isolated state dir, `tasks list --active` prints exactly two lines for the running and queued jobs, plus a separate `interrupted: 1` note. `tasks list --json` stays byte-compatible with today's output.
- Workaround requested/authorized: none needed. The nested `target` reuse was explicitly approved by the user for this experiment. No cache-policy environment variable was overridden.
