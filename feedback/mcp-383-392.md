- Job ID(s): 383, 384, 388, 391 (clippy), 385, 389, 392 (full test suite), 387 (MCP smoke

  tool against the shared daemon)
- Outcome: no facility defect; one friction point (blocker field scope) below
- Redacted command, cwd type, resource class: `cargo clippy --offline --locked -j 2
  --all-targets -- -D warnings` and `cargo test --offline --locked -j 2` (compile
  class, own worktree); `/bin/sh -c 'target/debug/tasks mcp --no-start-daemon <
  session.jsonl'` and `/bin/echo hello-from-mcp` (run class, own worktree)
- What was exercised: real execution of all jobs above. 383 failed on my own
  clippy finding (`manual_range_patterns` in a new test), 384/388 passed, 385/389
  passed; after the last change 391 (clippy) and 392 (all suites) passed (ignored
  tests listed in the task report). 387 passed but
  exposed a bug in MY code (tool replies were suppressed once stdin hit EOF);
  fixed and covered by `responses_are_sent_after_stdin_closes`. 390 was
  submitted, approved, admitted, run and waited for entirely through MCP
  (Submit -> ApproveCommand -> StartWorker -> Job polling -> Logs).
- Expected: compile jobs queue under pressure, run jobs admit on run gates.
- Observed: 388 logged "Native admission waiting: memory PSI some/full ..." and
  waited about 20 s before the compile slot, as intended. At the same moment
  `tasks status` (and therefore MCP `cluster_status`) showed
  `blocker: memory PSI full avg10 above 0.5%`, yet run-class job 390 was admitted
  with 0 s wait. That is correct per docs/design/cluster-snapshot.md (`blocker` is
  the compile-gate blocker only), but the snapshot carries no run/offload blocker,
  so an agent reading `cluster_status` may wrongly think run-class work is blocked
  too. `tasks admission` has `run_pressure_blocker`/`offload_pressure_blocker`;
  `cluster_status` now always adds them (`blockers: {compile, run, offload}`,
  read from the local admission report) as a stopgap.
- Impact: low; possible wrong "everything is blocked" conclusions by agents.
- Suggested improvement: move that into the snapshot itself: an additive `machine.blockers: {compile, run, offload}`
  to the v1 snapshot (feature/metrics owns it), keep `blocker` unchanged.
- Acceptance test for suggestion: with fake PSI where memory-full exceeds the
  compile threshold but not the run threshold, `tasks status --json` reports
  `blockers.compile` non-null and `blockers.run` null; existing fixture readers
  still parse.
- Workaround requested/authorized: none needed; no gate bypassed. The ignored
  real-daemon E2E (`tests/mcp.rs::real_daemon_submit_and_wait`) was not run,
  because, like the other worker E2Es, it should run outside `tasks run`.
  Job 390 covers the same path against the shared daemon.
