# Trial feedback: metrics sampler work, worker offload, daemon CPU cost

- Agent/session: `metrics` subagent, worktree `task-manager-worktrees/metrics`, branch `feature/metrics` (from `feature/osvauld-foundation` deda5ea).
- Job ID(s):
  - Laptop offload clients 331, 332, 333, 334, 337, 343, 344 -> LAN worker jobs 110, 111, 112, 113, 116, 119, 120.
  - Laptop queue: 340 (full test + clippy), 346 (cost measurement + full test + clippy), 350 (Python unittest, `--run`).
- Outcome: no coordinator defect blocked the work. Measured one significant cost issue in the installed daemon (below).
- Redacted command, cwd type, resource class:
  - `tasks run --offload --who metrics -- tasks-offload --worker <lan-worker> --who metrics --ssh-key <key> [--fetch tests/fixtures/snapshot] -- cargo test|clippy --locked -j 8`, live worktree, offload class.
  - `tasks run --who metrics -- sh -c 'cargo test --offline --locked -j 2 && cargo clippy ...'`, compile class.
  - The ignored real-worker E2E (`tests/status.rs`) was run directly as a prebuilt test binary, with isolated `TASK_MANAGER_STATE_DIR` and `TASKS_LOCK_DIR`, as the existing `closed_stdout.rs` convention says.
- What was exercised: real execution on both hosts. The installed runtime and daemons were not replaced or restarted.
- Expected: green tests/clippy on both hosts; fixtures fetched back via `--fetch`.
- Observed:
  - Offload worked smoothly: a cold worker compile took ~34 s; the `--fetch` of `tests/fixtures/snapshot` landed in `~/build-cache/offload/metrics/<remote id>/tests/fixtures/snapshot` (useful for generating files on the worker). A clippy failure surfaced as exit 101 on both job ids.
  - Daemon CPU (installed release dddc93c4, laptop, read from `/proc/PID/stat`): with two `tasks run` clients waiting, the daemon used ~41% of one core (414-431 ticks per 10 s). 40 sequential `tasks list` calls cost ~4.6 s of daemon CPU on top of that. Hypothesis, consistent with the code: each waiting `tasks run` client polls `List` and `Logs` every 250 ms; every request is served on a new thread and `handle()` loads the WHOLE ledger (`Store::jobs()`: one `SELECT` plus one execution query and JSON parse per row, ~340 rows) plus all estimates. `Logs` additionally loads the whole ledger again inside `worker::logs` (`database(&state)?.job(id)`). Measured `Store::jobs()` on a 304-row ledger: 8.9 ms (worker), 23 ms (laptop, debug build). That would explain "CPU in short-lived threads while jobs run".
  - The new sampler: one thread, one pass per tick; per-job targeted tree reads. Tick with 4 running jobs + 304-row ledger: 2.6 ms CPU (worker), 6.4 ms (laptop) = <= 0.33% of a core. A full `/proc` walk costs 4.2 ms (224 processes, worker) / 24 ms (391, laptop), so it runs only every 15th tick.
  - The E2E job waited ~35 s before running (real PSI gates on the busy laptop); expected behaviour, logged.
- Impact: daemon CPU scales with (waiting clients x ledger size); it will grow as history grows.
- Suggested improvement: have `wait_job` poll a single-job request (or the job's phase via one indexed row) instead of `List`; make `Store::job(id)` a single-row query; join executions in `Store::jobs()` (one query) or cache the listing per ledger `data_version`.
- Acceptance test for suggestion: with 1000 ledger rows and two waiting `tasks run` clients, daemon CPU stays below 5% of one core (measure via `/proc/PID/stat` over 30 s); `tasks logs ID` does not call `Store::jobs()`.
- Workaround requested/authorized: none. No gate was lowered, nothing deployed or restarted.
